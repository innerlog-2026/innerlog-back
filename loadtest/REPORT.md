# 외부 AI 호출 구간 동시성 개선 (sync blocking I/O → async)

> 백엔드 고도화 리포트 — 부하테스트로 병목을 재현하고,
> 리팩토링 전후를 동일 조건에서 측정해 정량 비교

## 1. 문제 정의

InnerLog는 예상 질문 생성·스피치 분석·면접 회고를 위해 외부 AI 서버를 HTTP로
호출한다. 이 호출은 **응답에 수십 초**가 걸린다(LLM/RAG). 초기 구현은 다음 구조였다.

- 모든 라우트가 **동기(`def`)** → Starlette가 anyio 스레드풀(기본 **40**)에서 실행
- AI 호출이 **동기 `httpx.Client`** → 응답 올 때까지 워커 스레드 점유
- 요청 스코프 DB 세션(`get_db`)이 **AI 호출 내내 커넥션을 점유**
- DB 커넥션 풀은 SQLAlchemy 기본값 **pool_size=5 + max_overflow=10 = 15**
- 배포는 **uvicorn 단일 워커**

→ 요청 1건이 AI 응답 시간(수 초~1분) 동안 **DB 커넥션 1개 + 스레드 1개**를 붙잡는다.
동시 요청이 늘면 15개 커넥션이 먼저 고갈되고, 이후 요청은 커넥션을 기다리다
`pool_timeout`(기본 30초)에 걸려 실패한다.

## 2. 실험 방법 (재현 가능)

| 항목            | 내용                                                                                   |

### 3-2. 판단 기준과 검증

**판단 기준**

- 회차 간 편차는 포화 구간의 동기 RPS에서 최대 약 15%(동시성 50: 4.21~4.92)였다. 이보다 작은 차이는 해석하지 않는다.
- 더 엄격하게, **비동기의 가장 나쁜 회차가 동기의 가장 좋은 회차보다 나은 레벨만** "개선"으로 본다.
  동시성 20 이상의 모든 레벨이 이를 만족한다(예: 50에서 비동기 최저 13.97 > 동기 최고 4.92 RPS).
  동시성 15 이하는 커넥션 풀이 포화되기 전이라 두 버전의 차이가 없고, 이는 예상과 일치한다.

**검증**

1. **이론값과 대조:** 동기 처리량 상한(6.6~6.9 RPS)이 리틀의 법칙 이론값(커넥션 15 ÷ 지연 2초 = 7.5 RPS)에 근접한다.
   병목이 커넥션 풀이라는 해석과 맞는다.
2. **로그로 원인 확인:** 동기는 매회 `QueuePool` 타임아웃이 75건 찍혔다. 클라이언트가 받은 500 40건과,
   클라이언트가 60초에 먼저 끊은 요청이 서버에서 뒤늦게 타임아웃 난 35건이다. 비동기 3회는 에러 0건.
3. **재현성:** 8월 1회 측정과 10월 3회 측정의 동기 결과가 같은 양상이다. 동시성 100의 실패 구성은
   네 번 모두 정확히 500 40건 + 타임아웃 60건이었다.
4. **백엔드 대기 시간 확인:** 비동기 p50은 동시성 100까지 2.09~2.32초(1회차 이상치 제외)로, 목 AI 지연 2초에
   백엔드 처리 시간이 거의 더해지지 않았다.
5. **기능 검증:** DB 단계를 옮긴 뒤 질문 추가 생성을 포함한 스피치 API 기능 검증 16개를 통과했다.

## 4. 원인 분석 (로그로 확정)

동기 버전의 500 에러는 커넥션 풀 고갈이 원인임을 백엔드 로그로 확인:

```
sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached,
connection timed out, timeout 30.00
```

AI 호출(2초) 동안 커넥션을 반환하지 않아, 동시 요청 16개째부터 풀(15)이 마르고
30초 대기 후 `TimeoutError` → HTTP 500. 남은 요청은 응답을 60초 내 못 받아 ReadTimeout.

## 5. 개선 내용

측정 대상 경로를 다음과 같이 리팩토링:

1. **AI 호출 비동기화** — 동기 `httpx.Client` → `httpx.AsyncClient` + `await`.
   AI 응답 대기 시간을 워커 스레드가 아닌 이벤트 루프에서 다중화.
2. **외부 호출 전 DB 커넥션 반환** — 서비스 로직을
   _(동기 DB 읽기 → `commit`으로 커넥션 반환) → (AI `await`, 커넥션 미점유) → (동기 DB 쓰기)_
   3단계로 분리. AI 대기 동안 커넥션 풀을 점유하지 않는다.
3. 라우트를 `async def`로 전환.
4. (2026-10 추가) **DB 읽기·쓰기 단계를 `asyncio.to_thread` 로 스레드에서 실행.** 커넥션을 기다리는 동안
   이벤트 루프가 멈추지 않게 함(7-4절).

관련 코드: [`app/services/speech.py`](../app/services/speech.py) 의
`_extract_questions_async`, `_read_generate_inputs`, `_save_new_questions`, `generate_more_questions_async`.

## 6. 시사점과 한계

### 시사점

- **느린 외부 I/O(AI·LLM 연동)에서 sync/async 선택은 취향이 아니라 처리량을 좌우하는 구조적 결정이다.** 응답이 수 초~수십 초인 호출을 동기로 처리하면, 소수의 동시 요청만으로 커넥션 풀이 고갈된다.
- **병목은 CPU가 아니라 "대기 중 점유한 자원"이었다.** 서버는 놀고 있는데도 커넥션이 없어 요청이 실패한다 → 스케일업(더 큰 서버)이 아니라 자원을 놓아주는 코드 구조로 풀린다.
- **정량화가 개선의 근거가 된다.** "빨라졌다"가 아니라 "동시성 50에서 4.4배, 100에서 실패율 100%→0%"(3-1절, 3회 중앙값)라는 재현 가능한 숫자로 말할 수 있다.

### 한계 (정직하게)

- **로컬 단일 머신 측정이다.** 부하 생성기·백엔드·목 AI·DB가 한 대(macOS)에서 돌고, 다른 앱의 백그라운드 부하도 섞인다.
  3-1절의 1회차 이상치가 그 예다. 그래서 3회 측정의 중앙값과 범위로 판단했다.
- **부하는 closed-loop 방식이다.** 응답을 받아야 다음 요청을 보내므로, 서버가 멈추면 요청 자체가 줄어 지연 지표에 덜 드러난다(7-4절).
- **숫자는 로컬 실측값이다.** 단일 워커 · 커넥션 풀 15 · AI 지연 2초 고정 가정이므로 절대치보다 **추세와 배수**로 읽어야 한다. AI 지연을 실제값(30~60초)으로 키우면 sync 붕괴 임계점은 더 낮은 동시성에서 나타나 대비가 더 극적이 된다. 즉 **2초는 sync에 유리한(개선폭을 과소평가하는) 보수적 조건**이다.
- **DB(SQLAlchemy)는 여전히 동기다.** async 라우트 안에서 `db.query()`가 그대로 실행되어 이벤트 루프를 수 ms씩 블로킹한다. 이번 부하(≤100 동시성)에선 AI 대기(2초)가 지배적이라 무시할 수준이지만, 처리량을 훨씬 더 올리면 이 동기 쿼리가 **다음 병목(대략 1 ÷ 쿼리시간)**이 된다. 완전한 async는 DB 호출을 스레드풀로 오프로딩(`run_in_threadpool`)하거나 async 드라이버(asyncpg + `AsyncSession`)로 가야 한다.
  → **7절 실험에서 이 문제가 실제 장애로 드러나** DB 단계를 스레드로 옮겼다. 이 실험은 새 질문이 0개인 상태(쓰기 없음)로만 측정해 드러나지 않았다.
- **전환한 것은 `generate_more_questions` 1개 엔드포인트뿐이다.** 나머지 AI 호출 경로(질문 최초 생성 `create_speech_practice`, 스피치 분석 `analyze_speech`, 면접 회고 `send_message`·`summarize`)는 아직 동기다. 같은 3단계 패턴을 전파해야 리팩토링이 완결된다.
  → 7절에서 스피치 분석·질문 최초 생성까지 전환했다. 면접 회고는 아직 동기다.

## 7. 후속 실험: 스피치 분석 전환과 장애 격리

### 7-1. 문제 정의

남은 동기 경로 중 가장 무거운 것은 **스피치 분석**(AI 응답 실측 약 110초)과 **질문 최초 생성**(30~60초)이다.
두 경로 모두 AI를 기다리는 내내 DB 커넥션 1개와 스레드 1개를 붙잡는다.

커넥션 풀(15)은 **모든 API가 함께 쓴다.** 스피치 분석이 15건 동시에 진행되면 로그인·지원 현황 조회처럼
AI와 무관한 API도 커넥션을 얻지 못한다. 인증(`get_current_user`)도 DB를 조회하므로 사실상 서비스 전체가 멈춘다.

이번 실험의 목표는 처리량이 아니라 **격리**다. 분석 자체의 속도·처리량은 AI 서버(STT를 CPU에서 수행)가
결정하므로 백엔드 전환으로는 바뀌지 않는다. 확인하려는 것은 "분석이 몰려도 나머지 서비스가 멀쩡한가"다.

### 7-2. 실험 방법 (재현 가능)

| 항목      | 내용                                                                                                   |
| --------- | ------------------------------------------------------------------------------------------------------ |
| 배경 부하 | `POST /speech-practices/questions/{question_id}/submissions` 를 동시에 N건 반복 (N = 0·5·10·15·20·30) |
| 프로브    | 같은 시간 동안 `GET /applications` 를 동시성 10으로 90초간 반복 → 처리량·p95·실패율                   |
| AI 서버   | Mock, 스피치 분석 **고정 지연 60초**                                                                   |
| DB        | PostgreSQL 16 일회용 컨테이너, 커넥션 풀 기본값(15, `pool_timeout` 30초)                               |
| 백엔드    | uvicorn 단일 워커 (프로덕션과 동일)                                                                    |

지연 60초는 실측(약 110초)보다 짧지만 커넥션 대기 한도(30초)보다 길어, 커넥션을 기다리는 요청이
한도 안에 커넥션을 얻지 못한다는 점에서 결과의 양상은 같다.

**판단 기준:** 배경 부하가 없는 N=0을 기준선으로 둔다. N=0끼리도 동기·비동기 실행 간 처리량이 약 10% 차이 났다
(548.5 vs 603.2 RPS, 프로브 경로는 두 버전이 같은 코드). 그래서 프로브 처리량·p95가 **같은 실행의 N=0 대비
±10% 안이고 실패가 0이면 "영향 없음"**으로 판단하고, 그보다 작은 차이는 해석하지 않는다.

하네스: [`isolation.py`](./isolation.py), [`run_isolation.sh`](./run_isolation.sh). 원자료:
[`results/isolation_sync.json`](./results/isolation_sync.json),
[`results/isolation_async_onloop.json`](./results/isolation_async_onloop.json),
[`results/isolation_async.json`](./results/isolation_async.json).

### 7-3. 결과 (sync → async)

| 동시 분석 | 프로브 RPS        | 프로브 p95             | 프로브 실패율   | 분석 성공/실패 |
| --------: | ----------------- | ---------------------- | --------------- | -------------- |
|         0 | 548.5 → 603.2     | 34ms → 27ms            | 0% → 0%         | — / —          |
|         5 | 589.4 → 613.4     | 28ms → 26ms            | 0% → 0%         | 10/0 → 10/0    |
|        10 | 568.9 → 612.5     | 27ms → 26ms            | 0% → 0%         | 20/0 → 20/0    |
|        15 | **0.4 → 611.9**   | **29,828ms → 26ms**    | **42.3% → 0%**  | 30/0 → 30/0    |
|        20 | **0.3 → 602.4**   | **29,856ms → 27ms**    | **44.4% → 0%**  | 35/24 → 40/0   |
|        30 | **0.1 → 596.3**   | **29,828ms → 27ms**    | **77.4% → 0%**  | 35/84 → 60/0   |

**핵심 관찰**

- **sync는 동시 분석 15건(= 커넥션 풀 크기)에서 정확히 무너진다.** 10건까지는 남는 커넥션 5개로 프로브가
  버티지만, 15건이 되면 프로브 처리량이 569 → 0.4 RPS로 떨어지고 p95가 `pool_timeout`(30초)에 붙는다.
  20건부터는 분석 요청끼리도 커넥션을 못 얻어 분석 자체가 실패한다(30건에서 119건 중 84건 실패).
- **async는 동시 분석 30건에서도 프로브가 분석이 없을 때와 같다.** 처리량 596~613 RPS, p95 26~27ms,
  실패 0건. 분석도 전부 성공했다(워커당 60초짜리 분석 2회씩, 30건 × 2 = 60건).

동기 버전의 실패 원인은 백엔드 로그로 확인했다. `http_500` 137건이 모두 커넥션 풀 고갈이다.

```
sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached,
connection timed out, timeout 30.00
```

`ReadError` 는 500 직후 서버가 닫은 keep-alive 연결을 클라이언트가 재사용하다 난 실패로,
500과 함께 늘어난다.

### 7-4. 중간에 발견한 문제 — 이벤트 루프 위의 동기 DB 호출

스피치 분석을 async로 전환한 첫 초안(커밋·배포 전 작업 단계)은 6절에서 한계로 적었던 구조 그대로였다.
AI 호출만 `await` 하고, DB 읽기·쓰기는 `async def` 안에서 동기로 실행했다. 이 초안의 결과가 [`isolation_async_onloop.json`](./results/isolation_async_onloop.json)이다.
이미 배포된 질문 추가 생성(`generate_more_questions_async`)도 같은 구조였다. 1~5절 실험은 새 질문이 0개인 상태라
DB 쓰기가 일어나지 않아 드러나지 않았다.

| 동시 분석 | 프로브 RPS | 60초 넘게 멈춘 프로브 | 분석 성공/실패 |
| --------: | ---------: | --------------------: | -------------- |
|         5 |      610.7 |                     0 | 10/0           |
|        10 |  **297.1** |                **10** | 14/2           |
|        15 |  **295.8** |                **10** | 23/2           |
|        20 |  **298.2** |                **10** | 12/20          |
|        30 |   **96.7** |                **20** | 9/21           |

동시 분석 10건부터 **프로브 10개가 한꺼번에 60초 넘게 멈추는** 구간이 생겼다. 서버 전체가 수십 초씩 정지한 것이다.
백엔드 로그에서 커넥션 풀 타임아웃이 `analyze_speech` 의 `db.flush()`, 즉 이벤트 루프 위에서 발생했음을 확인했다.

1. 분석 요청이 AI 응답을 받은 뒤 결과를 저장하려고 풀에서 새 커넥션을 요청한다.
2. 풀이 차 있으면 이 대기가 **이벤트 루프 스레드에서** 일어나 루프 전체가 최대 30초 멈춘다.
3. 그동안 다른 요청은 응답도 못 보내고, 커넥션 반납(`get_db` 정리)도 루프가 일정을 잡아줘야 실행되므로 반납되지 않는다.
4. 서로를 기다리다 30초 타임아웃이 나서야 풀린다.

**수정:** 세 경로(스피치 분석, 질문 최초 생성, 질문 추가 생성)의 DB 읽기·쓰기 단계를 `asyncio.to_thread` 로
스레드에서 실행해, 커넥션을 기다리는 동안에도 이벤트 루프가 계속 돌게 했다. 7-3의 async 결과가 수정 후 수치다.

이 문제는 **p95만 봤다면 놓쳤다.** 수정 전 버전도 프로브 p95는 25~26ms로 정상처럼 보였다. 멈춘 요청은
지연이 아니라 타임아웃(실패)으로 집계되기 때문이다. 처리량 절반 감소와 60초 타임아웃 건수에서 드러났다.

### 7-5. 검증

1. **판단 기준 적용:** 비동기는 모든 레벨에서 프로브 처리량이 N=0(603.2 RPS) 대비 -1.1~+1.7%,
   p95는 26~27ms(N=0 27ms)이고 실패 0건이라 "영향 없음" 기준을 만족한다.
   동기는 N=15부터 처리량이 N=0 대비 99.9% 감소해 기준을 크게 벗어난다.
2. **로그로 원인 확인:** 동기 버전의 `http_500` 137건(레벨별 20+20+15+27+55)이 백엔드 로그의
   `QueuePool` 타임아웃 137건과 정확히 일치한다.
3. **임계점과 설정값 대조:** 동기 버전이 무너지는 지점(동시 분석 15건)이 커넥션 풀 크기(15)와 같고,
   그때 프로브 p95(29.8초)가 `pool_timeout`(30초)과 같다.
4. **배경 요청 수 대조:** 배경 워커는 95초 시점까지만 새 요청을 보내고 요청 하나가 60초 걸리므로, 워커당 정확히
   2회 요청한다. 비동기의 분석 성공 수(10·20·30·40·60건)가 계산값 N×2와 정확히 일치해, 멈추거나 실패한
   분석이 없었음을 프로브와 별개로 확인했다.
5. **원인만 바꿔 재측정:** 7-4절의 정지 증상은 원인으로 지목한 부분(이벤트 루프 위의 DB 호출)만 스레드로 옮겨
   같은 조건에서 다시 측정했을 때 사라졌다. 관찰로 세운 가설을 개입 실험으로 확정한 것이다.
6. **기능 검증:** 전환한 세 경로에 대해 정상·중복(409)·검증 실패(400)·타인 리소스(404)·AI 장애(503, 업로드 파일 정리,
   실패 시 미저장) 16개 시나리오를 확인했다.

### 7-6. 시사점과 한계

**시사점**

- **async 전환의 효과는 "자원을 놓는 것"만큼 "이벤트 루프를 막지 않는 것"에 달려 있다.** `async def` 안의
  동기 I/O 한 줄이 서버 전체를 멈출 수 있고, 동기 버전보다 오히려 나쁜 장애 양상(전체 정지)을 만든다.
- **커넥션 풀은 공유 자원이라, 느린 경로 하나가 무관한 API까지 무너뜨린다.** 장애 격리는 느린 경로가
  공유 자원을 대기 시간 동안 놓게 만드는 구조로 얻는다.

**한계**

- **분석 속도·처리량은 바뀌지 않는다.** 실제 AI 서버는 동기 엔드포인트 + 단일 워커에서 STT를 CPU로 처리하므로,
  분석이 겹치면 건마다 느려진다. 이번 결과는 백엔드가 그 대기를 버티는 능력이지 분석 성능이 아니다.
- **로컬 단일 머신 측정이다.** 부하 클라이언트·백엔드·목 AI·DB가 한 대(macOS, 8코어)에서 돈다.
  절대 RPS는 환경에 따라 다르므로 같은 조건의 전후 비교로 읽어야 한다.
- **조건마다 1회만 측정했다.** 효과가 커서(0.4 → 612 RPS) 결론은 바뀌지 않겠지만, 회차 간 편차는 확인하지 못했다.
- **목 AI가 고정 지연이고 실패를 주입하지 않는다.** 실제 응답 시간 분포나 AI 오류가 섞일 때의 동작은 측정 범위 밖이다.
- **부하는 closed-loop 방식이다.** 7-4절처럼 서버 정지가 지연 지표에 덜 드러나므로 처리량과 타임아웃 건수를 함께 봤다.
- **`asyncio.to_thread` 는 기본 스레드풀(`min(32, CPU+4)`)을 쓴다.** 동시에 진행되는 DB 단계가 그보다 많으면
  스레드를 기다린다. 이번 부하(동시 분석 30건)에서는 문제가 없었다.
- **면접 회고(`/chat`, `/summarize`)는 아직 동기다.** AI를 기다리는 동안 커넥션을 붙잡는 같은 구조라, 같은 방식으로 전환해야 한다.
