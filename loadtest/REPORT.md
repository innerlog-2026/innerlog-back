# 외부 AI 호출 구간 동시성 개선 (sync blocking I/O → async)

> 백엔드 고도화 리포트 — 부하테스트로 병목을 재현하고,
> 리팩토링 전후를 동일 조건에서 측정해 정량 비교

## 1. 문제 정의

InnerLog는 예상 질문 생성·스피치 분석·면접 회고를 위해 외부 AI 서버를 HTTP로
호출한다. 이 호출은 **응답에 수십 초**가 걸린다(LLM/RAG). 초기 구현은 다음 구조였다.

- 모든 라우트가 **동기(`def`)** → Starlette가 anyio 스레드풀(기본 **40**)에서 실행
- AI 호출이 **동기 `httpx.Client`** → 응답 올 때까지 워커 스레드 점유
- 요청 스코프 DB 세션(`get_db`)이 **AI 호출 내내 커넥션을 점유**
- DB 커넥션 풀은 SQLAlchemy 기본값 **pool_size=5 + max_overflow=10 = 15**
- 배포는 **uvicorn 단일 워커**

→ 요청 1건이 AI 응답 시간(수 초~1분) 동안 **DB 커넥션 1개 + 스레드 1개**를 붙잡는다.
동시 요청이 늘면 15개 커넥션이 먼저 고갈되고, 이후 요청은 커넥션을 기다리다
`pool_timeout`(기본 30초)에 걸려 실패한다.

## 2. 실험 방법 (재현 가능)

| 항목            | 내용                                                                                   |
| --------------- | -------------------------------------------------------------------------------------- |
| 대상 엔드포인트 | `POST /speech-practices/{application_id}/questions` (AI 호출 + DB 커넥션 점유)         |
| AI 서버         | Mock 서버로 대체, **고정 지연 2.0초** (실제 LLM 비용·변동 제거 → 백엔드 동시성만 측정) |
| DB              | 로컬 PostgreSQL 16, 커넥션 풀 기본값(15)                                               |
| 백엔드          | uvicorn 단일 워커 (프로덕션과 동일)                                                    |
| 부하            | closed-loop, 동시성 5→100 스윕, 레벨당 20초                                            |
| 측정            | 처리량(RPS), p50/p95/p99 지연, 실패 수                                                 |

## 3. 결과

| 동시성 | RPS (sync→async)      | p95 지연 (sync→async)         | 실패 (sync / async) |
| -----: | --------------------- | ----------------------------- | ------------------- |
|      5 | 2.4 → 2.4             | 2,111ms → 2,150ms             | 0 / 0               |
|     10 | 4.3 → 4.7             | 2,475ms → 2,233ms             | 0 / 0               |
|     15 | 6.6 → 6.8             | 2,635ms → 2,354ms             | 0 / 0               |
|     20 | 6.8 → 9.1 (1.3x)      | 3,928ms → 2,415ms             | 0 / 0               |
|     30 | 6.9 → 12.9 (1.9x)     | 4,933ms → 2,614ms             | 0 / 0               |
|     50 | 4.7 → 20.2 (**4.3x**) | 13,959ms → 3,019ms (**-78%**) | 0 / 0               |
|    100 | **0.0 → 36.8**        | — → 4,014ms                   | **100 / 0**         |

**핵심 관찰**

- **sync 처리량 상한 ≈ 6.9 RPS.** 동시성 15~30 구간에서 ~6.9로 포화(정체)되고, 그 뒤로는
  동시성을 올려도 처리량은 제자리인 채 p95 지연만 치솟는다(요청이 커넥션 대기 큐에 쌓임).
  이론값과 일치: 유효 커넥션 15 ÷ 지연 2초 ≈ 7.5 RPS.
- **sync 동시성 50에서 스래싱, 100에서 완전 붕괴.** 성공 0건 / 실패 100건
  (HTTP 500 40건 + ReadTimeout 60건).
- **async는 동시성에 비례해 처리량이 선형에 가깝게 증가**(100에서 36.8 RPS, 여전히 상승 여력;
  효율은 요청당 0.47→0.37로 완만히 감소하는 약한 sub-linear). p95는 **2~4초 대에서 안정적**
  (고동시성 100에서도 4.0초에 머무름), **모든 구간 실패 0건.**

## 4. 원인 분석 (로그로 확정)

동기 버전의 500 에러는 커넥션 풀 고갈이 원인임을 백엔드 로그로 확인:

```
sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached,
connection timed out, timeout 30.00
```

AI 호출(2초) 동안 커넥션을 반환하지 않아, 동시 요청 16개째부터 풀(15)이 마르고
30초 대기 후 `TimeoutError` → HTTP 500. 남은 요청은 응답을 60초 내 못 받아 ReadTimeout.

## 5. 개선 내용

측정 대상 경로를 다음과 같이 리팩토링:

1. **AI 호출 비동기화** — 동기 `httpx.Client` → `httpx.AsyncClient` + `await`.
   AI 응답 대기 시간을 워커 스레드가 아닌 이벤트 루프에서 다중화.
2. **외부 호출 전 DB 커넥션 반환** — 서비스 로직을
   _(동기 DB 읽기 → `commit`으로 커넥션 반환) → (AI `await`, 커넥션 미점유) → (동기 DB 쓰기)_
   3단계로 분리. AI 대기 동안 커넥션 풀을 점유하지 않는다.
3. 라우트를 `async def`로 전환.

관련 코드: [`app/services/speech.py`](../app/services/speech.py) 의
`_extract_questions_async`, `_read_generate_inputs`, `generate_more_questions_async`.

## 6. 시사점과 한계

### 시사점

- **느린 외부 I/O(AI·LLM 연동)에서 sync/async 선택은 취향이 아니라 처리량을 좌우하는 구조적 결정이다.** 응답이 수 초~수십 초인 호출을 동기로 처리하면, 소수의 동시 요청만으로 커넥션 풀이 고갈된다.
- **병목은 CPU가 아니라 "대기 중 점유한 자원"이었다.** 서버는 놀고 있는데도 커넥션이 없어 요청이 실패한다 → 스케일업(더 큰 서버)이 아니라 자원을 놓아주는 코드 구조로 풀린다.
- **정량화가 개선의 근거가 된다.** "빨라졌다"가 아니라 "동시성 50에서 4.3배, 100에서 실패율 100%→0%"라는 재현 가능한 숫자로 말할 수 있다.

### 한계 (정직하게)

- **숫자는 로컬 실측값이다.** 단일 워커 · 커넥션 풀 15 · AI 지연 2초 고정 가정이므로 절대치보다 **추세와 배수**로 읽어야 한다. AI 지연을 실제값(30~60초)으로 키우면 sync 붕괴 임계점은 더 낮은 동시성에서 나타나 대비가 더 극적이 된다. 즉 **2초는 sync에 유리한(개선폭을 과소평가하는) 보수적 조건**이다.
- **DB(SQLAlchemy)는 여전히 동기다.** async 라우트 안에서 `db.query()`가 그대로 실행되어 이벤트 루프를 수 ms씩 블로킹한다. 이번 부하(≤100 동시성)에선 AI 대기(2초)가 지배적이라 무시할 수준이지만, 처리량을 훨씬 더 올리면 이 동기 쿼리가 **다음 병목(대략 1 ÷ 쿼리시간)**이 된다. 완전한 async는 DB 호출을 스레드풀로 오프로딩(`run_in_threadpool`)하거나 async 드라이버(asyncpg + `AsyncSession`)로 가야 한다.
- **전환한 것은 `generate_more_questions` 1개 엔드포인트뿐이다.** 나머지 AI 호출 경로(질문 최초 생성 `create_speech_practice`, 스피치 분석 `analyze_speech`, 면접 회고 `send_message`·`summarize`)는 아직 동기다. 같은 3단계 패턴을 전파해야 리팩토링이 완결된다.
